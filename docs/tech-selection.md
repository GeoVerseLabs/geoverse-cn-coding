# ADR-001 中国地址编码 v1 技术选型

- 状态：已采纳（v0.1.0）
- 日期：2026-10-14
- 参考：《地址解析与逆地理编码落地方案（国内 / 海外）》中的“国内方案”与“开源技术栈对照表”

## 1. 背景

参考方案给出的国内路线是“行政区划数据 + 中文解析 + Elasticsearch 检索 + PostGIS 逆地理”，并用天地图等 API 兜底。本次实现在此基础上增加两条硬约束：

1. **执行效率**：单次请求毫秒级，单机即可支撑业务峰值；
2. **部署简易**：尽量少的组件，能在内网、离线、私有化环境一键起服务。

需要覆盖的国内特性：

| 特性 | 例子 | 处理位置 |
|---|---|---|
| 行政区层级可省略、可用简称 | “广东深圳南山”“海淀区中关村” | `admin.py`：AC 自动机 + 层级动态规划 + 编码前缀补全 |
| 同名区县 | 北京/长春“朝阳区”、全国几十个“城关镇” | 先验打破平局，并保留 2~3 种解释交给检索用数据判定 |
| 旧名、撤并改名、县改区 | 崇文区、襄樊、密云县 | `data/admin/aliases.csv` + 自动生成“县/市 → 区”别名 |
| 民族自治地方简称 | “黔东南苗族侗族自治州”→“黔东南” | 按 55 个民族名逐级剥离 |
| 不设区的地级市、省直辖县级市 | 东莞、中山、儋州；济源、仙桃 | `AdminIndex.lineage` 特殊处理 |
| 中文无空格、中文数字 | “人民路三段十八号”“三号楼二单元” | `normalize.py`：只在量词前转换数字，不动“二七区”“十堰” |
| 门牌写法 | 上海“弄”、北京“甲 13 号”、“93 号院”、“3-2-501” | `parser.py` |
| 三套坐标系 | WGS84 / GCJ-02 / BD-09（天地图 CGCS2000≈WGS84） | `coords.py`，内部统一 WGS84，只在出入口转换 |
| 区划每年/半年变更 | 民政部年度发布、省级半年发布 | 区划数据是 CSV，替换后重建数据文件 |
| 合规 | 审图、测绘资质、不抓取商业图商 | 只内置政府公开区划代码；边界/POI 由使用方按合规来源导入 |

## 2. 备选方案

| | A. 参考文档全栈 | **B. 单体嵌入式（采用）** | C. PostGIS 单库 | D. Go 单二进制 |
|---|---|---|---|---|
| 组成 | FastAPI + ES 8（IK、拼音插件）+ PostgreSQL/PostGIS + Redis | FastAPI + SQLite（FTS5、R*Tree）+ Shapely + pyahocorasick | FastAPI + PostGIS（pg_trgm / zhparser） | Go + 嵌入式 KV/倒排 |
| 需运维的组件 | 4 个 | **1 个容器 + 1 个数据文件** | 2 个 | 1 个 |
| 最小内存 | ES 2–4 GB + PG 1 GB 起 | **约 100 MB / worker**（百万级 POI） | PG 1 GB 起 | 最低 |
| 每次请求的网络往返 | 解析 → ES → PG → Redis，3+ 次 | **0 次**（全部进程内） | 1 次 | 0 次 |
| 中文检索 | IK 词典分词，成熟；插件须与 ES 小版本严格对应 | 自定义 bigram + BM25 + 重打分，无词典依赖 | pg_trgm 对中文可用但排序弱；zhparser 需编译 | 需自研 |
| 空间能力 | PostGIS 全功能 | R*Tree 近邻 + GEOS STRtree 点落面，满足逆地理 | 全功能 | 需自研或绑 GEOS |
| 数据更新 | 在线增量写 | 离线重建（百万级约 1 分钟）+ 原子替换 | 在线增量写 | 离线重建 |
| 扩展上限 | 亿级、分布式 | 单文件数千万级；读多副本水平扩展 | 千万级 | 千万级 |
| 中文 NLP 生态（JioNLP、MGeo） | 可直接接入 | 可直接接入 | 可直接接入 | 需跨语言调用 |

## 3. 决策

采用 **B：单进程 Python 服务 + 单文件 SQLite**。

- 地理编码的在线负载是“只读、低延迟、高并发”，数据按天/周更新即可，不需要数据库的在线写能力；
- 把解析、检索、空间计算放在同一进程，省掉所有网络往返，延迟比多组件方案低一个数量级；
- 一个镜像加一个 `.db` 文件就是完整交付物，私有化/离线环境拷过去即可运行；
- 存储层集中在 `store.py`，查询接口很窄（全文检索、按路名取门牌、矩形范围查询），将来数据量或写入需求超出单机时，可以换成 PostGIS/ES 实现而不动解析和排序逻辑。

## 4. 各层选型

| 层 | 参考文档建议 | 本版选择 | 理由 |
|---|---|---|---|
| 区划数据 | 国家地名信息库 + 统计用区划代码 | 内置统计用区划代码 2023 版（省–乡四级，44,706 条，WTFPL 整理版）+ 别名表 | 开箱可用；统计局已停更，按文档建议后续跟民政部发布同步 |
| 行政区匹配 | pyahocorasick + 规则 | 同左，另加层级动态规划与多解释输出 | 一次扫描拿全部候选，0.05–0.5 ms/条 |
| 地址解析 | 规则词典为主，JioNLP 辅助，MGeo 难例 | 规则词典；JioNLP/MGeo 不进 v1 依赖 | JioNLP、MGeo 依赖重（后者需要深度学习运行时），留作离线评测与难例处理的扩展点 |
| 全文检索 | ES 8 + IK + 拼音 | SQLite FTS5 + 中文 bigram + BM25，候选再按 Dice 相似度、层级一致、门牌命中、热度重打分 | 免词典、对新词和简称不漏召回；不需要 JVM 和插件版本对齐 |
| 门牌 | — | B 树索引按（路名, 区县）取门牌，精确命中或同侧奇偶插值 | 门牌是国内准确率的关键，单独一条快路径 |
| 逆地理 | PostGIS `ST_Contains` / KNN | 边界：Shapely 2 STRtree（GEOS）；近邻：SQLite R*Tree + 球面距离 | 全国乡镇约 4 万个面，常驻内存查询微秒级 |
| 坐标转换 | WGS84/GCJ-02/BD-09 | 纯 Python（标量 math 版 + 建库用 numpy 向量版），GCJ-02 反算迭代 | 无依赖，6 µs/次 |
| 缓存 | Redis，H3 网格 | 进程内 LRU+TTL；逆地理按 1e-5° 网格取整 | 数据只读，副本各自缓存即可，少一个组件 |
| 兜底 | 天地图 / 商用 API，配额 + 熔断 | 天地图（标准库 urllib），每日配额 + 熔断 + 待审核日志回流 | 只在本地置信度不足且请求精度更细时调用 |
| API | FastAPI | FastAPI + uvicorn 多 worker | 解析用 Python，FastAPI 最省事 |
| 评测 | 金标准集 + 误差统计 | `cngeocoder eval`：区县准确率、P50/P90 误差、精度分布，可设阈值做 CI 卡口 | 每次改规则/换数据都跑 |

## 5. 实测性能

环境：本仓库开发容器（单核单线程，Python 3.13），`scripts/bench.py` 生成的合成数据（名称、坐标随机，只用来测性能）。

| 数据量 | 建库 | 文件 | 内存峰值 | 地址解析 | 正向·POI | 正向·门牌 | 逆地理 |
|---|---|---|---|---|---|---|---|
| 20 万 | 9.8 s | 48 MB | ≈100 MB | 0.07 ms | 0.26 ms | 0.22 ms | 0.13 ms |
| 100 万 | 57 s | 231 MB | ≈120 MB | 0.08 ms | 0.54 ms（P95 1.2） | 0.33 ms（P95 0.65） | 0.33 ms（P95 0.60） |

均为平均延迟、未命中缓存；内存峰值含建库过程。生产以 uvicorn 多 worker 部署，吞吐随 CPU 核数线性增加。

调优过程中的两个发现，已固化在实现里：

- FTS5 的 `content=''` 与 `detail='column'` 同时使用时 bm25 恒为 0，排序失效，因此保留 `detail='full'`；
- “大厦”“小区”“大道”这类高频 bigram 的倒排很长，建库时统计文档频率 ≥0.3% 的 token 写入 meta，查询时剔除；精确候选（门牌、路名）都落空时才做模糊路名检索。这两项把百万级 POI 查询从 3.4 ms 降到 0.54 ms，门牌查询 P95 从 10 ms 降到 0.65 ms。

## 6. 代价与升级条件

| 限制 | 影响 | 何时升级、升级到什么 |
|---|---|---|
| 数据只读，更新靠重建 | 不适合分钟级实时纠错回写 | 需要在线写入时，把 `Store` 换成 PostGIS 实现（方案 C） |
| 单文件规模 | 千万级以内表现良好 | 超过约 5000 万条或需要跨机分片时，检索换 ES（方案 A 的检索层） |
| 无拼音、无输入联想 | 只做“地址→坐标”，不做搜索框联想 | 需要联想时单独加 suggest 服务（ES completion / 拼音插件） |
| 规则解析的长尾 | 不规范地址（口语、错别字）召回下降 | 用评测集定位难例，再接 MGeo 做结构化或 query–POI 重排 |
| 行政区边界与 POI 未内置 | 开箱只有区划词典和少量示例点 | 按 `docs/data.md` 导入天地图边界、自有门牌/POI |

## 7. 与参考文档的差异

1. 全文检索从 ES+IK 换成 SQLite FTS5 + bigram：放弃词典分词的精细度，换来零外部依赖和更低延迟；排序质量由重打分弥补，评测集持续监控。
2. 空间计算从 PostGIS 换成 SQLite R*Tree + Shapely：逆地理只需要点落面和近邻，两者都能在进程内完成。
3. 缓存从 Redis 换成进程内 LRU：数据只读，没有一致性问题。
4. 保留文档中的核心设计：区划词典 + 三层解析结构、统一 WGS84 + `coordsys` 参数、低置信度兜底 + 配额熔断、金标准评测先行。
