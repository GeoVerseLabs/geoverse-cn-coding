# 口语化与非标准地址处理

口语化或不标准的写法也要尽量匹配到真实数据，同时给出可信的置信度：能直接用的给高分；拿不准的压到阈值以下，并说明原因、给出备选。代码集中在 `colloquial.py`（预处理、简称）、`parser.py`（方位、交叉口、纠错）、`geocoder.py`（变体比对、歧义、历史确认、置信度）。

## 1. 处理了哪些写法

| 类型 | 例子 | 处理 | 对置信度的影响 |
|---|---|---|---|
| 繁体字 | 上海市浦東新區世紀大道100號 | 地址常用字繁 → 简（约 570 字，不含“乾”等简体也用的字） | 无；`signals.traditional` 标记 |
| 收寄件口语 | 麻烦送到…谢谢、放菜鸟驿站、到了打电话、周末送货 | 删除嘱咐语；“白天鹅宾馆”这类正常名称不受影响 | 无；`signals.removed` 列出删掉的片段 |
| 儿化、口语楼层、表情 | 南锣鼓巷儿、8号院儿、负一楼、地下二层、🏢 | 去“儿”、楼层写成 B1层、删符号 | 无 |
| 城市别称 | 魔都、帝都、羊城、鹏城、蓉城 | `data/admin/nicknames.csv`，只在开头或紧跟其他行政区时生效 | 与简称同权重 |
| 行政区错别字 | 北京市海定区、朝杨区、杭州市余坑区 | 在已识别的上级下找只差一个字的地级/县级名称；无上级时全国唯一才纠 | 有数据落在纠正后的区县内则不扣分，否则 ×0.95（无上级约束的弱纠错 ×0.85）；`signals.corrections` |
| 历史旧名 | 崇文区、萧山市、万县市 | `history_aliases.csv` | 权重低于现行名称 |
| 子位置 | 北京西站南广场、上海火车站南广场出口、B出口 | 生成去掉子位置的查询变体（单独的“广场”不去，避免“万达广场”→“万达”） | 变体 ×0.97 |
| 门、塔楼 | 北大东门、望京SOHO塔3 | 门进 `extra`，塔楼进 `building` | 无 |
| 简称、俗称 | 北大、人大、北师大、工体、上海站、首都机场 | 数据别名（`alias` 列）+ 建库按规律生成的简称（`abbr` 列） | 生成简称 ×0.9 |
| 城市名嵌在 POI 名里 | 上海中心大厦（被切成 上海 + 中心大厦） | 比对时把行政区名接回去，也把候选名里用户已写出的城市前缀去掉再比 | 去前缀 ×0.97；只剩类别词（“火车站”）的不比 |
| 省略中间字 | 腾讯大厦 → 腾讯滨海大厦、阿里西溪 → 阿里巴巴西溪园区 | 4 字以上、全部字按序出现时给分 | 相似度 0.45 + 0.3 × 长度比 |
| 方位位移 | 天安门往东五百米、XX 北侧 200 米 | 按方位角和距离从参照点位移 | ×0.9（超过 1 km ×0.8）；`relation.anchor_location` 给出参照点 |
| 附近、对面 | 国贸附近、北京站对面 | 坐标取参照点 | ×0.92；`relation.radius_m` 给出范围（300 / 100 m） |
| 参照物 + 目标 | 望京SOHO对面的星巴克 | 先定位参照物，再在 2 km 内找目标，越近越优先 | 找不到目标时返回参照物，置信度封顶 0.55，`signals.target_not_found` |
| 交叉口 | 王府井大街与东长安街交叉口 | 两条道路几何求交；不相交但相距 150 m 内取最近点中点 | 精度 `intersection`，0.95（间隙求中点 0.85） |
| 历史确认过的写法 | 测试路那个红色大门的院子 | 查历史确认库（见第 3 节） | 按确认次数和离散度给 0.9 以上 |

## 2. 防止“自信地错配”

放宽匹配容易把没有的地方匹配到相似的地方。几道保护：

1. **辨识词检查**：查询里有辨识度的词（去掉类别词和行政区名后的字），在候选所有名称里都没出现时，相似度打 6 折。例如“上海虹桥火车站”不会高置信度匹配“上海火车站”。
2. **类别词不单独作依据**：去掉城市前缀后只剩“火车站”“中心大厦”这类类别词的名称变体不参与比对。
3. **省略写法只认 4 字以上**：“北京南站”不会匹配“北京西站”。
4. **同名歧义**：分数接近（差 0.06 以内）、相距 2 km 以上的同名 POI，在没有区县或位置上下文时，置信度降到 0.55 以下，`alternatives` 返回备选。传 `city` 或 `focus` 即可消歧。
5. **精度不足封顶**：只匹配到比输入更粗的层级（要 POI 只到区县）时，置信度不超过 0.55。

按约定，**置信度 ≥ 0.6 可直接采用**，0.55 左右表示“有结果但需确认”，再低表示只到区划级或不可靠。服务端兜底（天地图）也在 0.6 以下才触发。

## 3. 历史确认结果闭环

口语写法千变万化，规则覆盖不完，最可靠的是“这个写法以前被确认过在哪”。

1. 业务确认坐标时（签收、司机打点、人工核验）调用 `POST /v1/feedback`：

   ```bash
   curl -X POST http://127.0.0.1:8000/v1/feedback -H 'content-type: application/json' \
     -d '{"address":"测试路那个红色大门的院子","location":"116.3005,39.9581","coordsys":"gcj02","source":"签收"}'
   ```

   需要配置 `GEOCODER_FEEDBACK_LOG`。接口只追加 JSONL，不改在线数据。
2. 下次建库时导入：`cngeocoder build ... --memory var/feedback.jsonl orders_confirmed.csv`（CSV 字段 `address,lng,lat[,coordsys,count]`）。
3. 建库按两个键聚合：归一化原文、标准化写法（含方位描述）。同一写法的多次确认取中位点，并计算离散度。
4. 查询时先查确认库。
   - 离散度 ≤ 30 m 记为门牌级，≤ 150 m 记为 POI 级，超过 300 m（多处签收、写法本身有歧义）不采用；
   - 分数 = 0.88 + 0.05 × log10(次数 + 1) − 离散度 / 3000。

确认库里的“方位描述”是键的一部分，“北京站对面”的确认点不会被当成“北京站”。

## 4. 结果里的说明字段

```json
{
  "precision": "poi",
  "confidence": 0.882,
  "relation": {"type": "offset", "bearing": 90, "distance_m": 500.0, "text": "往东500米",
               "anchor": "天安门", "anchor_location": {"lng": 116.3912359, "lat": 39.9072908}},
  "signals": {"similarity": 1.0, "matched_by": "name"},
  "alternatives": [{"name": "…", "location": {…}, "adcode": "…", "address": "…"}]
}
```

| 字段 | 含义 |
|---|---|
| `signals.corrections` | 行政区纠错：原文、纠正后名称、编码，以及是否为弱纠错 |
| `signals.traditional` / `signals.removed` | 做过繁简转换 / 删掉的口语片段 |
| `signals.matched_by` | 命中方式：`name`、`alias`、`abbreviation`、`name_without_city`；去掉子位置后命中会带 `+sublocation` |
| `signals.similarity` | 名称相似度（0–1） |
| `signals.admin_from_data` | 输入没写区县，行政区由命中的数据补全 |
| `signals.competitors` | 同名歧义的备选数量，备选详情在 `alternatives` |
| `signals.target_not_found` | “X 对面的 Y”中没找到 Y，返回的是参照物 X |
| `relation` | 方位关系：类型、参照物、位移参数或大致范围 |

## 5. 评测

`data/eval/colloquial_sample.csv` 包含 30 条口语化正样本（覆盖上表各类写法）和 7 条负样本（数据里没有的地点：北京南站、上海虹桥火车站、首都国际机场等）。改动前后在同一示例数据上对比：

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 高置信度且正确（≤ 1 km） | 80.0% | 100% |
| 高置信度且正确（≤ 300 m） | 73.3% | 100% |
| 高置信度但错误（≤ 300 m 口径） | 3 条 | 0 条 |
| 负样本被拒绝 | 85.7% | 100% |
| 区县准确率 | 90.0% | 100% |
| 正确结果的平均置信度 | 0.838 | 0.915 |

改动前的失败主要在繁体、子位置、省略写法、方位位移、交叉口，以及“望京SOHO隔壁的711”被高置信度返回成望京SOHO。

**这组数字需要打折看**：样本只有 37 条，而且和规则是一起写出来的，示例数据也只有 30 个地点，结果偏乐观。上线前应从真实业务里抽取口语化地址（按城市和写法分层，1,000 条以上），用 `cngeocoder eval <文件> --max-confident-wrong 0` 做卡口，重点盯“高置信度但错误”这一项。

性能影响（单线程平均）：20 万条合成数据下 POI 检索 0.26 → 0.36 ms、门牌 0.22 → 0.26 ms；100 万条下查询延迟基本不变（POI 0.54 ms、门牌 0.32 ms），建库因生成简称从 57 s 增至 79 s。

## 6. 已知限制

- 错别字只纠地级、县级名称中的一个字；乡镇、道路、POI 名称的错别字靠相似度兜，同音多字错误（“海定”与“海淀”以外的复杂情况）没有拼音模型支撑。
- 简称只覆盖规律性强的几类（大学、体育场馆、火车站、机场、去城市前缀）。其他俗称（“鸟巢”“水立方”）需要在数据的 `alias` 列维护，或靠确认库积累。
- “附近”“对面”的范围（300 m、100 m）是经验值，没有按场景区分。
- 同名歧义依赖调用方提供 `city` 或 `focus`；只靠地址文本无法区分时，只能降置信度并给出备选。
- 繁简转换只覆盖地址常用字，生僻繁体字会原样保留。
